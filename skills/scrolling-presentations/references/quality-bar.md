# Quality bar

Judge the rendered presentation, not just the code.

## Content

- Each chapter answers one useful question for the intended audience.
- Primary documentation supports product claims; recommendations and illustrative architectures are identified as such.
- Short headings and diagram labels carry the message. Longer nuance is available without crowding the default view.
- Tool overlap and optional components are explicit. No invented live data, performance measurements, or completed integrations.

## Visuals and interaction

- Inspect desktop and narrow mobile screenshots; check clipping, horizontal overflow, typography, spacing, icons, and reading order.
- Test next, previous, restart, direct step selection, autoplay completion, and pause/resume when present.
- Test every recommendation choice, disclosure, demo reset, and navigation anchor affected by edits.
- A citation inside a collapsed source section must open it before scrolling there.
- Motion has an explanatory purpose. It does not hide essential text or require scrolling at a particular speed.
- Support keyboard focus and reduced motion. Stop unnecessary work offscreen and when the page is hidden.
- Remove unsupported controls instead of leaving silent no-ops.

## Portability

- Open the delivered route after the final reload. Check all assets load.
- Do not require a local account name, absolute file path, running app, API key, or proprietary browser tool to view the static presentation.
- Keep source/attribution notices with reused assets. Do not assign a blanket license to third-party work.
- Package only the presentation files and required assets. Verify the extracted bundle works independently of the original project.

Report only checks actually performed. A screenshot review is not a full accessibility audit, and a local prototype is not a deployed integration.
